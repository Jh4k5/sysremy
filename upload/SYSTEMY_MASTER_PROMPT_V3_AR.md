# SYSTEMY — MASTER PROMPT V3
## تطوير المنتج القائم وفق معيار منتج عالمي: موثوق، مترابط، قابل للتخصيص، وقابل للاشتراك

> **مهم:** هذه وثيقة قيادة تنفيذ، لا إذن لإعادة كتابة التطبيق كله. اقرأ كامل الملف والوثائق المتاحة ثم نفّذ المرحلة 0 فقط. لا تواصل إلى المراحل التالية من تلقاء نفسك.

## 0. الدور والهدف

أنت تعمل بصفتك فريقًا متكاملًا من مهندس تقني رئيسي، ومصمم تجربة هاتف، ومهندس بيانات، ومراجع أمن، ومهندس جودة، ومدير منتج. مهمتك تطوير تطبيق **Systemy** الموجود أصلًا، لا إنشاء بديل تجريبي.

الهدف: تحويل Systemy إلى نظام حياة شخصي عربي أولًا، يبدأ من الإدخال السريع والوضوح المالي، ثم يربط المال والوقت والعادات واليوميات والأهداف والدراسة والعمل دون تكرار البيانات أو إرهاق المستخدم.

لا تدّعِ أن التصميم أو عدد الأنظمة سيصنع تقييمًا بمليارات الدولارات. ابنِ خصائص تجعل المنتج جديرًا بالاعتماد اليومي: قيمة واضحة، سلوك موثوق، حفظ آمن، سرعة، خصوصية، عودة طبيعية، واشتراك اختياري يقدم قيمة إضافية حقيقية.

## 1. بوابة المصدر — لا تتجاوزها

المصدر التقني السابق المعروف هو Next.js + React + Dexie/IndexedDB + غلاف Android Java/WebView. توجد لقطات حديثة للواجهة ولقطة Repomix جديدة اسمها `repomix-output(1).xml` لا تحتوي ملفات مصدر داخل `<files>`؛ لا تُعاملها مستودعًا كاملًا.

في أول جلسة:
1. اعرض Git remote والفرع وHEAD وحالة git والـpackage manager وlockfile وإصدارات Node/Bun وأوامر build الحالية.
2. اعثر على المصدر الأصلي المطابق للواجهة/APK الحالية. اربط كل لقطة بالمكون ومسار الحالة والـhandler والـdatabase table الذي يُفترض أن يخدمها.
3. قارن APK والويب ونسخة المصدر. إذا لم يتطابق المصدر مع اللقطات أو لم تتوفر ملفات البناء اللازمة، **توقف عن التعديل** واطلب المصدر الصحيح/نتيجة التصدير الصحيحة.
4. افحص الاختبارات الحالية، lint، TypeScript، web build، Android build عندما يكون تشغيلها ممكنًا. اكتب النتائج كما حدثت فعلًا.
5. افحص الأسرار في المصدر والحزم وAPK وسجل Git من دون طباعة أي قيمة. إذا وجد مفتاح مكشوف، دوّره/أبطله لدى المزود يدويًا إن احتاج إذن المالك، ولا تكرر قيمته.
6. لا تغيّر الملفات في هذه المرحلة. قدّم خريطة المسارات والأزرار والأنظمة وحالة كل ميزة وخطة PRs.

**لا تنفذ إلا المرحلة 0 الآن، ثم توقّف واعرض التقرير.**

## 2. قواعد لا يجوز خرقها

- لا تستبدل التطبيق بـ Expo/React Native أو Prisma/SQLite دون قرار معماري منفصل وموافقة صريحة.
- لا تنشئ قاعدة بيانات موازية للمعاملات والمهام والعادات والوجبات والملاحظات الموجودة.
- لا تعتبر وجود Component أو Table أو Screenshot دليلًا على أن الميزة تعمل.
- لا تعرض نجاحًا قبل نجاح الحفظ الفعلي.
- لا تجعل AI يكتب مباشرةً إلى قاعدة البيانات. المسار هو: نص خام → تحليل → مسودة قابلة للتعديل → تأكيد → خدمة النظام الحالية → حفظ → تحديث الشاشات → تراجع حيث يمكن.
- لا تستخدم بيانات تجريبية بصمت فوق بيانات المستخدم، ولا تمسح بيانات أو تعيد seed دون إذن واضح.
- كل تغيير مخطط بيانات يملك Dexie migration مرقّمًا واختبارًا للترحيل والنسخ القديمة.
- الحسابات المالية حتمية ومختبرة، وليست ناتج LLM. استخدم integer minor units ولا تستخدم floating point في تخزين/حساب المال.
- لا ترسل اليوميات أو الخزانة أو الصحة إلى خدمة سحابية دون موافقة واضحة حسب نوع البيانات.
- PIN ليس تشفيرًا. لا تصف أي ملف بأنه مشفر ما لم يُنفذ التشفير واختباره.
- لا تحجب تصدير بيانات المستخدم الكامل أو حذفها خلف اشتراك مدفوع.
- لا تضف رسومًا ثقيلة أو blur/glow مستمرًا. احترم الأجهزة الضعيفة وتقليل الحركة.
- كل زر أو بطاقة أو أيقونة إعداد يجب أن تملك فعلًا صحيحًا. لا أزرار شكلية ولا toasts وهمية.

## 3. استراتيجية المنتج

### 3.1 الوعد الأساسي

**«سجّل ما يحدث في حياتك في ثوانٍ، وافهم أثره، واعرف خطوتك التالية.»**

المدخل الأساسي للاستخدام هو المال + Universal Capture. يجب أن ينجح المستخدم في تسجيل مصروف أو دخل دون إعداد حساب مصرفي، ثم يرى الأثر المالي فورًا مع شرح الحساب. توسيع الأنظمة يأتي بعد إصلاح موثوقية هذا المسار.

### 3.2 المستخدمون الأساسيون

صمّم ثلاثة مسارات تهيئة قصيرة قابلة للتخصيص:
- **الطالب:** مصروف محدود، الدراسة والمهام، هدف ادخار.
- **الموظف/المستقل:** دخل والتزامات ومشاريع وتوقع نقدي.
- **منظّم الحياة:** اليوميات والعادات والأهداف والروتين.

لا تفرض قالبًا من هذه القوالب؛ يمكن للمستخدم تعديل اختياراته في أي وقت. لا يتطلب بدء التسجيل إنشاء حساب سحابي.

### 3.3 لحظة القيمة الأولى

خلال أقل من دقيقة، يجب أن يستطيع المستخدم اختيار العملة، تسجيل أول دخل/مصروف أو بدء سجل يدوي، ورؤية تحديث صحيح فوري. إذا كانت البيانات غير كافية لحساب «المتاح الآمن»، اعرض «أكمل بيانات الميزانية» أو «تقدير أولي» بدل رقم يوحي بدقة غير موجودة.

## 4. الأنظمة — 14 وحدة منتج، على موجات

الأنظمة ليست 14 تطبيقًا منفصلًا تقنيًا. كلها تعتمد على مصدر بيانات وخدمات مشتركة، ولكل وحدة تجربة مستقلة من الخارج.

1. **المال والمحفظة:** العمليات، الحسابات، التحويلات، الميزانيات، الالتزامات والاشتراكات، الديون، الأصول، صافي الثروة، التوقعات والتقارير. لا تُحسب التحويلات دخلًا/مصروفًا، ولا تُحسب دفعة الالتزام مرتين.
2. **المهام والوقت والتركيز:** Inbox، اليوم، القادم، الأولويات، التكرار، المهام الفرعية، الفلاتر، الوقت المخطط/الفعلي، التركيز.
3. **العادات والروتين:** عادات نعم/لا/كمية/مدة، تكرار مرن، روتين متعدد الخطوات، تسجيل بنقرة، راحة/إيقاف مؤقت، سجل واتجاهات.
4. **الصحة والجسم:** نوم، طاقة، مزاج، ماء، وزن وقياسات، تمرين، تذكيرات أدوية شخصية، تقارير اختيارية دون تشخيص طبي.
5. **العقل واليوميات:** يوميات مؤرخة، مزاج وعوامل، قوالب صباح/مساء، كتابة وصوت/صور، بحث خاص، ذكريات، قفل وخصوصية.
6. **التعلم والدراسة:** المقررات، المهام، الامتحانات، خطة رجعية، الدرجات والأوزان، بطاقات مراجعة متباعدة، جلسات دراسة وموارد.
7. **الأهداف والادخار:** أهداف مالية وغير مالية، معالم، نتائج قابلة للقياس، مراجعات، سيناريوهات، روابط بمهام/عادات/مشروعات. الهدف المالي يرتبط بوعاء/حساب المال ولا ينشئ رصيدًا وهميًا.
8. **المشاريع والعمل الحر:** مشاريع، مراحل، Kanban، وقت، عملاء، دخل ومصروفات مرتبطة، فواتير بسيطة؛ كل دخل/مصروف يُسجّل في نظام المال مرة واحدة.
9. **الأشخاص والعلاقات:** مناسبات، تذكير تواصل، ملاحظات اختيارية، ديون/تقسيمات مرتبطة بالمال، دون استيراد جهات اتصال بلا إذن.
10. **المنزل والأسرة:** التزامات، فواتير، صيانة، ضمانات، ممتلكات، تسوق، قوائم ومسؤوليات. المدفوعات تنشئ transaction مرتبطة لا نسخة ثانية.
11. **الإيمان — اختياري بالكامل:** تقويم هجري وخطط عبادة/قرآن/أذكار/رمضان عند تفعيل المستخدم، وفق مصادر موثوقة؛ لا تفترض دين المستخدم.
12. **الملاحظات والمعرفة:** ملاحظات دائمة غير مؤرخة، وسوم ومجلدات، روابط ومرفقات، معرفة قابلة للبحث وتحويل إلى مسودة مهمة/مصروف/حدث.
13. **المستندات والخزانة:** ملفات ووثائق وتواريخ انتهاء ووسوم وربط بالعناصر، OCR لاحقًا مع مراجعة النتائج، حماية ونسخ احتياطي قابل للاستعادة.
14. **السفر والتجارب:** رحلات، خط سير، ميزانية عملة أجنبية، مهام تجهيز، حجوزات مرتبطة بالخزانة، وملاحظات/ذكريات.

**الفصل الدلالي الإلزامي:** اليوميات = سجل زمني؛ الملاحظات = معرفة دائمة. المهام = أفعال؛ المشاريع = سياق ومخرجات ومصروفات مرتبطة. الأهداف تحدد النتائج؛ أماكن حفظ المال الحقيقية تبقى في المال. التقويم والبحث والتذكير والذكاء الاصطناعي واستوديو التخصيص قدرات مشتركة، وليست بطاقات أنظمة إضافية.

### 4.1 موجات الطرح

- **Wave 0:** تدقيق المصدر والأمان والاختبارات.
- **Wave 1:** إصلاح Quick Add + التنقل + مصدر حقيقة المال + منع التكرار. لا ميزات جديدة قبل اجتيازها.
- **Wave 2:** إكمال المال والمهام/الوقت والعادات واليوميات والأهداف والتعلم كشرائح عمودية مترابطة، وإعادة استخدام الوحدات الموجودة.
- **Wave 3:** الصحة والمشاريع والمنزل والأشخاص.
- **Wave 4:** الإيمان الاختياري والمعرفة والخزانة والسفر، ثم مزامنة آمنة وقوالب متقدمة.

لا تعرض نظامًا غير مكتمل على أنه نشط. ضعه في معرض قوالب واضح يشرح أنه تجريبي/قادم. لا تجعل عدد الصفحات شرطًا آليًا للاكتمال؛ الشرط هو اكتمال الرحلات والبيانات والاختبارات.

## 5. التنقل والواجهة

### 5.1 شريط التنقل

حافظ على خمسة مواضع كحد أقصى على الهاتف: **اليوم، نظام مثبت افتراضيًا هو المال، +، التقويم/التدفق، المزيد/أنظمتي**. يمكن تخصيص المواضع لاحقًا، لكن يجب أن تكون الأيقونة والاسم والوجهة والحالة النشطة متطابقة دائمًا. لا تعرض أيقونتي تقويم أو عين مكررتين دون داعٍ.

### 5.2 شاشة اليوم

ترتيب البداية الافتراضي:
1. رأس مختصر واحد: تحية + التاريخ؛ زر الخصوصية واحد، إشعارات، مساعد.
2. Hero «المتاح الآمن اليوم» مع الفترة ومصدر البيانات وزر «كيف حُسب؟».
3. زرا مصروف/دخل أو فتح الالتقاط.
4. اقتراح واحد مناسب ومسنود بالبيانات.
5. التالي (حتى 3 عناصر).
6. عادات اليوم إن كانت مفعّلة.
7. مزاج/ملاحظة/Insight كأقسام قابلة للإخفاء.

لا تعرض كروت ضخمة فارغة. كل Widget قابل للإخفاء والترتيب، لكن لا تفتح إعدادات معقدة عند أول تشغيل.

### 5.3 مركز «أنظمتي»

- بحث حقيقي عن الأنظمة والمحتوى، مع فلاتر: مثبتة، نشطة، مخفية، قوالب.
- صف حتى أربعة أنظمة مثبتة يعرض مؤشرًا حيًا مفهومًا.
- شبكة متجاوبة: عمودان عادة، عمود واحد إن ضاق عرض 320px، وثلاثة على الشاشة الكبيرة عند ملاءمة العرض.
- البطاقة: أيقونة صغيرة، اسم، وصف قصير، مقياس واحد مع معنى واضح، وآخر نشاط اختياري.
- **الضغط على البطاقة** يفتح Overview للنظام الصحيح.
- **أيقونة الإعدادات** تفتح إعدادات هذا النظام تحديدًا.
- **قائمة المزيد** تعرض فقط إجراءات منفذة: تثبيت/فك، ترتيب، إخفاء، تغيير اسم/أيقونة، أرشفة أو استعادة. لا تحذف بيانات لمجرد إخفاء النظام.
- لا تستخدم «0 متتبع» إذا كان النظام لا يحتوي مفهوم المتتبعات؛ اعرض «لم يُهيّأ بعد» مع زر بداية.
- كل نظام قادم لا يظهر في النشط. يظهر في معرض قوالب بعلامة حالته، دون زر ميت.
- احفظ الترتيب والأنظمة المخفية/المثبتة في قاعدة البيانات المحلية واستعدها بعد إعادة التشغيل.

## 6. عقد التفاعل لكل نظام

كل وحدة مطروحة يجب أن توفر، بما يناسب طبيعتها:
- Overview بمقاييس مشتقة من سجلات حقيقية.
- إضافة وعرض تفاصيل وتعديل وأرشفة/حذف مؤكد وتراجع عند الإمكان.
- بحث وفلاتر وفرز.
- إعدادات فعلية محفوظة.
- حالات loading/empty/populated/dense/error/offline/locked حيث تنطبق.
- روابط لأنظمة أخرى تحدث فورًا عند حفظ أو تعديل أو حذف.
- اختبارات CRUD والترحيل والاستعادة وRTL/LTR.
- تصدير أو بيان شفاف لحدود التصدير.

اكتب ملفًا/ثابتًا مركزيًا يربط `SystemId` بمسار المكوّن وبحالة الطرح والمقاييس وأفعال بطاقة النظام. لا تكرر منطق التوجيه داخل كل بطاقة. أضف اختبارًا آليًا يتأكد أن كل عنصر مرئي له فعل صحيح.

## 7. Universal Quick Add (+) — أولوية P0

### 7.1 التصميم المطلوب

- يفتح بنقرة واحدة لوحة خفيفة أو Full-screen sheet فقط إن تطلبت لوحة المفاتيح ذلك.
- رأس ثابت: مقبض، «إضافة سريعة»، زر إغلاق واضح.
- حقل نص طبيعي في الأعلى: «اكتب ما تريد تسجيله… مثال: قهوة 18، دخل 500، ذكّرني بالإيجار».
- أزرار صوت/كاميرا فقط إذا كانت مدعومة فعليًا وبعد الإذن.
- أنواع في شبكة متجاوبة 2–3 أعمدة: مصروف، دخل، مهمة، ملاحظة، عادة، حدث. تحت «المزيد»: وجبة، ماء/طاقة، مستند، هدف، التزام، مخزون، وغيرها مما يعمل فعلًا.
- **تحكم واحد فقط لنوع العملية.** لا تعرض اختيار مصروف/دخل في شريط ثم تكرره تحت المبلغ.
- نموذج مصروف/دخل: المبلغ، العملة، الحساب، الفئة، التاريخ، وصف اختياري. عدم وجود حساب لا يمنع الإدخال؛ أنشئ/استخدم «نقد» افتراضيًا بشكل آمن أو اسمح بسجل غير مرتبط بحساب إذا كانت البنية الحالية تقتضي ذلك، من دون تغيير صامت للرصيد.
- لوحة رقمية LTR دائمًا: `1 2 3 / 4 5 6 / 7 8 9 / . 0 ⌫`.
- وصف/ملاحظة قابل للإدخال، وزر «حفظ» ثابت أسفل الجزء المرئي وفوق لوحة المفاتيح.
- حفظ معطّل فقط أثناء الكتابة. أضف «حفظ وإضافة آخر» عند الحاجة.

### 7.2 لا تخمن سبب التعليق

قِس وقت الفتح والكتابة والحفظ، سجل Console errors وunhandled rejections، افحص React renders، استعلامات Dexie، global Zustand subscriptions، drawer lifecycle، viewport/keyboard resize، وحمل الرسومات. اختبر الفتح والإغلاق المتكرر والأجهزة الضعيفة. عالج الجذر الذي تثبته القياسات؛ لا تضف timeouts عشوائية.

### 7.3 اختبارات Quick Add

- فتح + 20 مرة وإغلاقه دون لوحات مكررة أو تدهور تدريجي.
- نقر متكرر على حفظ لا ينتج سجلات مكررة.
- تجارب: `قهوة 18`، `دخل 500`، `ذاكرت بايثون 45 دقيقة`، `أضف كوبين ماء`، `ملاحظة: فكرة مشروع`، `حوّلت 200 من النقد للبنك`؛ التحويل ليس مصروفًا ولا دخلًا.
- مبلغ مفقود/غير صحيح، لا فئة، فشل DB، شبكة منقطعة، لوحة مفاتيح مفتوحة، رجوع Android، وإلغاء مسودة.
- اختبر 320×720 و360×800 و393×873 و430×932 CSS px، ثم APK حقيقي.
- حفظ محلي يعمل بلا إنترنت؛ فشل AI لا يمنع الإدخال اليدوي.

## 8. مصدر حقيقة المال

- استخدم خدمة مركزية واحدة للحسابات، الميزانيات، safe-to-spend، الأهداف المالية والتقارير.
- المبلغ مخزن بوحدات العملة الصغرى كعدد صحيح. كل سعر صرف يحمل عملة المصدر/الهدف، السعر، المصدر، وتاريخ السعر.
- أنواع العمليات واضحة: expense/income/transfer/refund/adjustment/commitment settlement.
- التحويل الداخلي لا يغير مجموع الدخل/المصروف؛ تسوية الالتزام ترتبط بالمعاملة ولا تتكرر.
- المعادلة المعروضة يجب أن تطابق الحساب البرمجي وتاريخ الفترة. إذا كانت البيانات ناقصة، اعرض مستوى كفاية/تقدير بدل الدقة الزائفة.
- إذا كانت شاشة اليوم تستخدم إعداد دخل شهري بينما شاشة المال تنتظر حسابًا حقيقيًا، فإما توحيد مصدر الحقيقة أو توضيح أن الأول تقدير منفصل. لا تعرض الرقمين بصيغة متناقضة.
- اكتب اختبارات للدخل صفر، والعجز، والعمليات الملغاة، والشهر المالي غير التقويمي، وتغيير العملة، والتحويل، والفائض المرحّل، والتسويات وعدم العد المزدوج.

## 9. بنية البيانات والروابط

- حافظ على Dexie كمخزن محلي قائم ما لم يثبت تدقيق منفصل ضرورة الهجرة.
- استعمل typed domain services لكل نوع: Transactions, Tasks, Habits, Journal, Goals, Health وغيرها. لا تكتب من الواجهة مباشرةً إلى الجداول في كل مكان.
- النظام المخصص يستخدم تعريفات/حقول/عروض محددة وآمنة؛ لا تحول المال والصحة والخزانة إلى جداول JSON عامة.
- كل سجل له ID مستقر، createdAt/updatedAt، حالة أرشفة/حذف مناسبة، ونطاق مالك/مساحة إذا أُضيفت مشاركة لاحقًا.
- علاقات عينة: فاتورة ↔ تقويم/تذكير ↔ معاملة عند الدفع؛ مشروع ↔ مهام ↔ مصروفات/دخل؛ هدف ↔ مهام/عادات/وعاء؛ وصفة ↔ قائمة تسوق ↔ مسودة مصروف؛ شخص ↔ دين/معاملة؛ مستند ↔ معاملة/أصل/رحلة.
- لا تضف نظام أحداث/graph عامًا ضخمًا قبل توثيق احتياجات النسخة الحالية. ابدأ بعلاقات typed واضحة، وأضف جدول links عامًا فقط حيث يوجد احتياج مثبت.
- أي Dexie migration يملك export/backup قبلها، واختبار ترحيل من قاعدة حقيقية قديمة، واختبار استعادة backup قديم.

## 10. الذكاء الاصطناعي Sys

- قواعد محلية حتمية أولًا للحالات الواضحة؛ AI اختياري للحالات الغامضة وبموافقة معالجة سحابية.
- مخرجات AI هي Draft typed، مع قيمة الحقول والثقة والحقول الناقصة؛ لا تعتمد confidence المولّد من النموذج كدليل جودة وحيد.
- كل كتابة تتطلب تأكيد المستخدم. الحذف/التحويل/المشاركة وتغيير البيانات الحساسة تتطلب تأكيدًا إضافيًا.
- أي Insight مالي/شخصي يحتاج نطاقًا زمنيًا ومعرفات الأدلة `evidenceIds` ومصدر الأرقام. إذا لم توجد بيانات كافية، اذكر ذلك.
- لا تحسب المال داخل LLM، ولا تدخل الخزانة أو اليوميات السرية في السياق افتراضيًا.
- أضف rate limits، تحقق schema، سقف حجم الطلب، logging آمنًا، واستراتيجية fallback محلية. لا يظهر أي مفتاح AI في JavaScript أو APK أو source map.

## 11. استوديو التخصيص

نفذ تدريجيًا، لا دفعة واحدة:

**Stage A:** داكن/فاتح/AMOLED/تلقائي، accent محدود بتباين صالح، حجم خط، كثافة مريحة/مدمجة، Reduce Motion. حفظ واستعادة.

**Stage B:** وضع تعديل صريح لترتيب/تثبيت/إخفاء عناصر اليوم وبطاقات الأنظمة، مع حفظ/إلغاء ومعاينة. لا يبدأ السحب عند نقرة عادية.

**Stage C:** ترتيب تبويبات النظام، العرض الافتراضي، الحقول المخصصة، الفلاتر المحفوظة، الويدجتات وقواعد أتمتة آمنة.

كل إعداد يجب أن يغير الواجهة أو يملك زر حفظ واضحًا. Reset appearance لا يمسح البيانات. Reset layout لا يمسح السجلات. انتقل بين Minimal/Balanced/Power دون فقدان بيانات.

## 12. الاشتراك والاحتفاظ

لا تصمم «إجبارًا على الاشتراك». صمم سببًا يستحق الدفع:
- **Free:** الإدخال اليدوي، سجل مال أساسي، مهام وملاحظات وعادات أساسية، عمل محلي، تصدير/حذف البيانات، ووظائف الأنظمة المطروحة.
- **Plus:** مزامنة مشفرة فعلية بين الأجهزة، مشاركة عائلية بصلاحيات، تحليلات/توقعات متقدمة، حقول وأنظمة وأتمتة غير محدودة، حدود AI أعلى، OCR، وويدجتات متقدمة.
- لا تحجب القدرة على تسجيل مصروف أو إكمال مهمة، ولا تصدير/حذف البيانات.
- لا تعرض اشتراكًا مباشرًا حتى يعمل نظام الفوترة وتُختبر حالات النجاح والفشل والإلغاء واستعادة المشتريات.
- Onboarding يعرض قيمة شخصية وليس قائمة ميزات طويلة. المستخدم يصل لأول فائدة قبل paywall صلب؛ اختبر نموذجًا بتجربة زمنية واضحة، سعر، مدة، التجديد، وإلغاء سهل.
- بعد الاشتراك، وجّه المستخدم فورًا إلى أول فائدة مدفوعة وراقب الإلغاء المبكر. لا تعتبر التحويل نهاية رحلة المنتج.
- اجعل أي تسعير فرضية اختبار؛ لا تختر سعرًا نهائيًا بلا بحث مستخدمين وبيانات سوق.

## 13. التصميم والأداء

- الهوية داكنة عميقة/فاتحة اختيارية، أسطح متمايزة، لون دلالي محدود، بدون توهج في كل بطاقة.
- رأس واحد واضح، وهرم بصري، وبطاقات مدمجة بارتفاع محتواها. لا تكرر زر الخصوصية.
- شريط التنقل لا يغطي المحتوى. أضف padding للمحتوى مساويًا لارتفاعه + safe area + هامش.
- كل عنصر تفاعلي >=44–48px، aria label، حالات focus وkeyboard/back واضحة.
- لا ترندر كل النماذج الثقيلة في Quick Add وهو مغلق. لا تحمّل كل الجداول لفتح اللوحة.
- جرّب الأداء على Android ضعيف/ويب فيو، واحترم `prefers-reduced-motion`.
- إذا كان TypeScript build errors متجاهلًا، أصلح ذلك في المرحلة المناسبة ولا تعد نجاح build دليلًا وحيدًا.

## 15. شروط القبول النهائية

- صفر أزرار ميتة في السطح النشط؛ اختبار آلي لكل عنصر تفاعلي.
- لا نظام نشط يفتح placeholder أو شاشة بلا إجراء إنشاء.
- لا سجلات مالية/مهام/وجبات مكررة بسبب الربط أو إعادة المحاولة.

- البيانات محفوظة بعد إغلاق/إعادة تشغيل APK، والنسخ الاحتياطي قابل للاستعادة.
- اختبارات المعادلات المالية تمر؛ القيم المعروضة تأتي من الدوال التي تملك المعادلة.
- لا أسرار في حزم العميل أو APK أو source maps.
- كل إعداد تخصيص محفوظ وذو أثر فعلي.
- لا مرفقات/يوميات حساسة تذهب إلى AI دون الموافقة.
- لا overflow في 320/360/393/430 CSS px، ولا محتوى خلف الشريط السفلي.
- لا يُذكر اختبار على أنه ناجح ما لم ينفذ فعلًا. سجّل بيئة الاختبار والـcommit والنتيجة.
